# Android performance preparation
Local photo decoding and encoding now use a module-scoped exclusive job gate across component mounts. Cancellation discards stale results but retains the gate until the previous browser operation and resource cleanup finish. New selections during that interval are rejected with a retry message, rather than queued. The original file is sliced with the validated MIME type instead of creating a second byte-array-backed Blob. Decoded bitmap resources are released before JPEG encoding; canvas backing memory is cleared in finally. Preview maximum side is 1200 px (at most 1.44 million pixels, nominal 5.76 MB RGBA backing store, excluding browser overhead). Existing input limit of 24 megapixels still applies, so full decoding may temporarily use substantial memory; the browser is not guaranteed to decode at reduced resolution. No claims about actual Android peak memory or latency are made. Browser hangs can hold the gate until the page is reloaded; do not force-unlock while decoding is unresolved.
Mannequin and outfit geometry are memoized; form controls use larger touch targets and a single column at narrow widths. Five new regression tests cover job serialization, idempotent cleanup, aspect ratios, bounded pixel allocation, and implementation guardrails. No new dependencies or paid services.
## Device acceptance still needed
On Android Chrome and Samsung Internet, use non-sensitive sample photos: portrait/landscape JPEG, PNG, invalid file, oversized image, EXIF rotated camera photo. Repeatedly select/cancel, switch products and leave/reenter. Verify no stale preview, correctly oriented images, readable controls at 320/360/412 CSS pixels, no horizontal scroll, smooth outfit changes, and no photo network traffic. Measure actual decode/encode duration and memory with appropriate browser tooling where available. A physical device test has not been run. Photographic AI inference and actual retailer asset support remain deferred.
