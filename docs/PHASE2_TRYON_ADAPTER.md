# Photographic renderer adapter — Phase Two
Commercial clearance and actual model evaluation deferred by owner. Do not enable a provider until those gates are complete.
## Implemented
scripts/tryon/offlineRendererAdapter.mjs defines an offline-only integration contract, gated on the evaluation report from the preceding step. It has no provider, credentials, network endpoint or customer photo access by default. The injected provider receives only private test fixture identifiers, case ID and AbortSignal. Results are constrained to same-case private artifact references, image MIME metadata, size and output hash. The adapter returns an explicit unavailable result for invalid inputs, errors, timeouts and cancellation; concurrent work on the same adapter instance is blocked until the provider settles. A result never verifies fit.
## Provider integration remaining
A future backend implementation must register an independently approved provider and immutable, trusted evidence and resolve private fixture IDs itself. It must validate actual file signatures, decoded dimensions, hashes and ownership against stored bytes, enforce process-wide quotas and timeouts, discard late outputs, isolate credentials, and handle cleanup and retention. This contract validates metadata only; it cannot guarantee that a provider honors cancellation or deletes outputs. Never expose this offline module directly to a client or accept client-supplied clearance metadata.
## Customer photo work may proceed independently
Prepare local consent, photo selection/quality validation, cancellation and removal UX without transmitting or storing new photos for rendering. Only after a real approved renderer and private access/deletion path are verified should authenticated requests connect to it. Keep existing chart-based size guidance independent and keep synthetic mannequin demo labeled as illustrative. No production API, database, infrastructure or third-party model has changed.
